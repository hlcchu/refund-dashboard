# Key decisions

Decisions that shape the design, why they were made, and when to revisit them. Add new entries
at the end. Don't rewrite old ones; mark them superseded instead.

| # | Decision | Why | Revisit if |
|---|---|---|---|
| 1 | Standalone web app in a container, not Power Apps | Shows the workflow without Power Apps licences or Dataverse. All rules run on the server, so no client can bypass them. | The customer wants to keep a Power Apps front end. It can call the same API. |
| 2 | Python (FastAPI). One image serves both the API and the UI. | The team is most familiar with Python. One image is simplest to run locally and on Azure. | The UI grows into a separate SPA with its own release cycle. |
| 3 | Server-side RBAC with four Entra app roles: Maker, Checker, Finance, Admin | Roles live in the customer's identity provider and every API call checks them. | Internal audit must be independent of Finance. Split `Refund.Auditor` back out. |
| 4 | Finance is read-only and includes the audit trail. There's no separate Auditor role. | Finance needs the same views an auditor would: refunds, exports, audit trail and chain check. | Same as #3. |
| 5 | Maker-checker is enforced per request by user ID, so a user holding both roles still can't approve their own refund. | Separate roles alone don't stop one person doing both. Blocked attempts are audited. | — |
| 6 | Two different checkers are needed only for refunds strictly above $50.00 | The customer requirement. Admin can change the threshold at runtime, and each change is audited. | — |
| 7 | Admin manages settings only. It can't raise, approve or view refunds. | Otherwise Admin would be a way around maker-checker. | — |
| 8 | Immutable audit uses three layers: an app hash chain, an Azure SQL ledger database (append-only `audit_events`), and SQL ledger fingerprints in write-once (WORM) Blob storage | App code alone can't stop someone with database access. The ledger and WORM storage make tampering detectable, even by a database admin. | — |
| 9 | **Retain records for 6 years:** yearly full SQL backups kept 6 years (`backupRetentionYears = 6`), and ledger fingerprints kept 6 years in WORM storage (`ledgerDigestRetentionDays = 2190`). | Aligned with the IRS's 6-year look-back period. Fingerprints are kept as long as the backups, so any restored backup can still be checked for tampering. | Legal or finance policy requires longer. IRS guidance is generally 3 years, 6 years if income is under-reported by more than 25%, and 7 years for bad-debt or worthless-securities claims; other regulators may differ. Both settings are one-parameter changes. |
| 10 | Hosting uses Container Apps, Container Registry, Azure SQL, Blob storage, Log Analytics and Application Insights. There's no Key Vault. | Managed services with scale-to-zero and no secrets to store: the app reaches SQL, the registry and storage with a managed identity. | A secret is introduced, e.g. a payment-provider key. Add Key Vault then. |
| 11 | The app and Azure SQL run in the same region. `sqlLocation` is a fallback only. | Splitting regions adds latency to every database call and cross-region data charges. The live test used Central US for SQL only because East US refused new SQL servers on a new subscription. | Never for production. Fix the region instead: pick one that accepts SQL, or request access through Azure support. |
| 12 | Monitoring uses Application Insights plus four alerts: API 5xx errors, SQL load, replica restarts, and a failed audit-chain check | Failures and tampering need to reach a person, not just sit in logs. | — |
| 13 | Network lockdown (private network, private endpoints, no public SQL) is in [path-to-production.md](path-to-production.md), not the default templates | The customer hasn't confirmed they'll deploy on Azure. The demo templates stay simple and cheap. | The customer commits to deploying on Azure. |
| 14 | Azure Front Door with a web application firewall is out of scope | Internal tool. The Premium tier has a list-price base fee of about $330/month, and IP restrictions cover the internal-access case for free. | The app is exposed to external users or the public internet. See [path-to-production.md](path-to-production.md). |
| 15 | Out of scope: paying out refunds, per-currency limits, notifications | Keeps the first version focused on the approval control. | Customer requirements change. |
